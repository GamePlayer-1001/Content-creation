# 为什么提示词高手最后都会走向工作流沉淀

去年这个时候，我手机里收藏了 312 条提示词。

是真的数过，因为后来我做了一件特别二的事——把它们一条条翻出来重新测了一遍。结果是有 187 条已经完全失效，模型对它没反应；有 94 条还能跑，但输出质量比当时差了一大截；真正还能"按当初效果"出活的，只剩 31 条。

这是去年 11 月到今年 4 月，五个月的时间。

我开始意识到一件事：在大模型这个赛道里，"我会写提示词"这个能力，可能比我们想象的要不值钱得多。它有点像 2010 年前后那批靠刷 SEO 关键词吃饭的人，技巧本身没问题，但底层平台一改算法，整个手艺就得推翻重学。

## 一、提示词不是技能，是耗材

很多人把提示词当成一种"积累"。

收藏夹里存一堆，按场景分好类——文案、翻译、代码、长文摘要、PPT 大纲。仿佛只要存得够多，就总有一天能用得上。我一开始也这么干，最夸张的时候在 Notion 里建了一个 8 个分类、40 多个子标签的提示词库，每周末花两小时整理。

后来发现这个库的更新速度根本追不上失效速度。

GPT-4 升级到 GPT-4o，里面一半的"长文生成万能模板"立刻就废了——模型行为变了，原来需要靠咒语逼出来的能力变成了默认能力，你那段精心设计的 system prompt 反而成了拖累。Claude 3.5 升到 3.7 Sonnet 那次更明显，很多搞角色扮演的提示词输出突然变得啰嗦，因为新版本的"安全护栏"判定逻辑动了。

我现在的看法是：

**提示词的生命周期，比我们以为的短一个数量级。** 它不是固定资产，是耗材，跟打印机墨盒一个性质。你能做的不是攒墨盒，是把整个打印流程理顺，让墨盒坏了能马上换。

## 二、真正赚钱的人，早就不在研究提示词了

这个判断不是我拍脑袋来的。

我加过三个不同方向的"AI 变现"社群——一个是做小红书矩阵的，一个是跨境独立站的，还有一个是做企业内训的。三个群我都潜水了两个多月，认真翻所有的实操分享。

得出的结论非常一致：群里真正在出货、有月流水的那部分人，几乎没人在群里讨论提示词。他们聊的全是另外一类东西。

小红书矩阵那个群，头部玩家在分享什么？

- 怎么用 Coze 把"选题→大纲→正文→封面→标签"五个环节串起来；
- 哪个云服务器跑无头浏览器最便宜；
- 多账号矩阵怎么用指纹浏览器隔离；
- 一批新号怎么用养号 SOP 跑过审核。

提示词只是这个流水线里的某一个零件——而且通常是最不重要的零件。因为只要你的整个流程跑得通，某一个节点的提示词哪怕只有 60 分，整体出货质量也是稳定的；反过来，提示词写到 95 分，但流程不通，照样一个号都做不起来。

跨境独立站那个群更典型，主流话题是 GEO（生成式引擎优化）怎么布局、Cloudflare Worker 怎么挡爬虫、Stripe 风控怎么过——AI 在这套打法里就是一台引擎，引擎本身好不好不是关键，关键是车架、底盘、油路全都得在。

## 三、什么时候你会意识到必须搭工作流

这事儿不是看文章看出来的，是被坑出来的。

我自己第一次真切感受到必须沉淀工作流，是去年帮一个朋友做企业内训材料。任务是把 200 多份内部访谈纪要整理成 12 个主题的培训手册。我当时的方案非常典型的"提示词高手"思路——写了一段巨长无比的 system prompt，号称"一键产出培训章节"。

第一份手册花了三个小时，效果还不错，朋友很满意。

第二份开始出问题。同样的提示词，输入换了一批访谈，输出的章节结构突然变得跟第一份不一样了——有些小标题缺失，有些段落顺序错乱。我花了一下午调提示词，调到第二份能跑了。结果到第三份，又出新问题。

做完第五份的时候我崩溃了。

回头看，我做错的是一件根本性的事：我把所有的"流程要求"全压在一段提示词里，让模型一次性完成 9 件不同的工作（分类→提取→去重→摘要→重组→润色→加案例→配标题→检查格式）。模型本来就不擅长在一轮对话里干 9 件事，每次稍微有点输入差异，就会有 1–2 件事掉链子。

后来我把它拆成了 7 个独立步骤，每一步只让模型干一件事，中间用 Python 脚本做数据流转和校验。整套东西在 Dify 上搭了大概一天半。

剩下的 200 份纪要，三天跑完。零返工。

这件事之后我对"工作流"才有了真正具体的理解：**它不是花哨的概念，它是用"分工 + 校验"换"稳定性"的一种工程手段。**

## 四、一个能"沉淀下来"的工作流，长什么样

聊聊我自己现在在用的几条标准。这不是教科书定义，是我自己被坑出来的经验。

**第一条：每一步只让模型干一件事。**

如果某一步你让模型同时"提取要点"又"重写成口语化"，那它一定会在某些输入下翻车。拆开。提取是提取，改写是改写。中间用变量传递。

**第二条：每一步都要有 fallback。**

模型偶尔抽风是常态，工作流的鲁棒性来自你对抽风的预案。比如某一步输出 JSON 时偶尔会带 markdown 代码块，你就在下一步前加一个清洗函数；某一步偶尔会拒答，你就准备一个 retry + 换模型的分支。

**第三条：能用代码就别用模型。**

去重、格式化、计数、字符串替换、按规则筛选——这些事写 5 行 Python 比写 50 行提示词稳定一百倍。新手特别容易犯的错就是"什么都喂给模型"，因为感觉很酷。但每多用一次模型，就多一份不确定性。

**第四条：把版本和配置外置。**

提示词写在代码里就是定时炸弹，模型一更新你就得改代码。我现在所有的提示词都放在 YAML 里，每个版本打 tag，能 A/B 切换。模型名也是配置项，不是硬编码。这条说起来简单，做到的人很少。

**第五条：交付物要可审计。**

每一步的中间输出都要落盘存一份，至少保留 7 天。一旦最终结果出问题，你能往回倒查到底是哪一步炸了。没有这个，你永远只能干瞪眼。

满足这五条，才算真的把流程沉淀下来。否则那只是一堆零散的提示词，加了个调度脚本，挂了"工作流"这个名字而已。

## 五、新手怎么入门

最低成本的版本，不需要任何工具，一个 Markdown 文档就够。

打开一个新文档，把你做某件事的步骤一条条写下来。每一步标清楚：

- 输入是什么；
- 用什么模型、什么提示词；
- 期望的输出是什么样；
- 输出不对的话，怎么处理。

这就是 1.0。下次再做同样的事，照着这个文档一步步走。跑十遍之后，你会清楚地知道哪几步特别烦、特别重复、特别容易出错——那几步就是你下一阶段要自动化的目标。

工具方面，国内能用的 Coze 和 Dify 都够，前者更傻瓜，后者更灵活；国外 n8n 是开源自部署的天花板，Make（原 Integromat）适合连接 SaaS。如果你完全不想碰这些可视化工具，直接 Python + LangChain 也行，但学习曲线陡一些。

选哪个不重要。重要的是你开始把脑子里那套流程"外化"出来——一旦外化，它就开始能被迭代、被复制、被交接、被审计。

## 写在最后

去年开始我就没再花时间研究"史诗级提示词"了。

不是因为它们不香，是因为我意识到一件事：在这个赛道里，单点技巧的衰减速度太快，你今天磨出来的咒语，可能三个月后连作者自己都觉得过时。但工作流不一样——只要你的拆解是合理的、每一步的职责是清晰的、模型只是其中一个可替换的节点，那么不管底层 GPT 升到 6 还是 Claude 升到 5，你这套东西的骨架都还在。

护城河不是某条神秘的提示词。

护城河是你比别人早半年开始把流程画清楚，然后用三个月跑通了第一版，再用半年迭代到现在的样子——这个过程没法靠看一篇文章追上来。
