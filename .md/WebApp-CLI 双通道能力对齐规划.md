# 内容生成输出项目 - WebApp / CLI 双通道能力对齐规划

更新时间：2026-03-19
状态：规划文档（重写版，替代“职责边界”口径）

---

## 一、结论

这项目里，**WebApp 和 CLI 不应该按职责拆分**，而应该按**交互形态**区分。

也就是说，不是：
- WebApp 负责一部分
- CLI 负责另一部分

而是：
- **WebApp 和 CLI 都应拥有完整流程的查看、使用、编辑、推进能力**
- 二者的区别，只在于交互方式不同

一句话原则：

> **WebApp 和 CLI 是同一套系统的双通道，不是被切开的两套职权系统。**

---

## 二、为什么要改成这个口径

### 1. 真实使用关系决定了两边都必须完整
- WebApp 是老大主要使用的操作面
- CLI 是二哈 / Agent 主要使用的操作面

既然双方都需要真正推进任务，那就不能把系统设计成：
- 一个能完整做事
- 一个只能辅助做半套

### 2. 如果按“职责切分”设计，会人为割裂系统
这样会导致：
- WebApp 有一套完整体验
- CLI 只能跑局部动作
- 同一任务很难在两个通道之间切换
- 后续维护时会不断出现能力不对齐

### 3. 正确的区分维度是“交互方式”而不是“权限归属”
因此应该重新定义：

#### WebApp
是**完整图形界面**

#### CLI
是**完整命令界面**

二者面对的是同一条主流程、同一套状态、同一组产物。

---

## 三、双通道的核心原则

### 原则 1：能力全对齐
WebApp 和 CLI 都应支持完整主流程：

1. 读谷歌表格的热点列表
2. 选热点
3. 录入热点详细内容
4. 生成母稿
5. 多平台改写
6. 审核优化 / 去 AI 味
7. 生成多张配图
8. 排版
9. 导出图文结果并可打开

说明：
- 两个通道都应具备完整查看权
- 两个通道都应具备完整编辑权
- 两个通道都应具备完整流程推进权

### 原则 2：差异只在交互形态
#### WebApp 的优势
- 图形化展示更直观
- 连续浏览更自然
- 多版本对照方便
- 图片 / 排版 / 文件预览更适合
- 文本细修和可视化检查更舒服

#### CLI 的优势
- 命令式操作更快
- 更适合 Agent 批量使用
- 更适合脚本化与自动化
- 更适合组合执行、局部重跑
- 更适合记录结构化日志

### 原则 3：能力可以重复，逻辑不能重复
这里要特别强调：

> **能力重复可以，逻辑重复不行。**

意思是：
- WebApp 和 CLI 都能做完整流程
- 但底层绝不能各自维护一套独立业务逻辑

正确形态是：
- 同一套 shared services
- 同一套 pipeline
- 同一套 task state
- 两个不同前端入口

### 原则 4：允许同一任务跨通道切换
理想使用形态应该是：
- 老大在 WebApp 做到第 4 步
- 二哈在 CLI 接着看第 5 步并修改
- 再回到 WebApp 预览第 8 步排版结果
- 最后在任一通道执行导出

这意味着：
- 任务必须共享状态
- 阶段产物必须统一存储
- 两个通道必须能读写同一份任务上下文

## 四、双通道共同面对的主流程

这条主流程是两个通道共享的正式主路径：

1. **读谷歌表格的热点列表**
2. **选热点**
3. **录入热点详细内容**
4. **生成母稿**
5. **多平台改写**
6. **审核优化 / 去 AI 味**
7. **生成多张配图**
8. **排版**
9. **导出图文结果并可打开**

说明：
- 这 9 步不是 WebApp 专属
- 也不是 CLI 专属
- 而是整个项目的统一流程模型

## 五、WebApp 作为完整图形界面，应具备的能力

### 1. 完整流程查看能力
- 查看热点列表
- 查看热点详情
- 查看母稿与平台稿
- 查看审核前后版本
- 查看图片结果
- 查看排版预览
- 查看导出结果

### 2. 完整流程编辑能力
- 选热点
- 补录热点详细内容
- 修改母稿
- 修改平台稿
- 调整审核优化结果
- 重选图片 / 重生成图片
- 调整排版参数

### 3. 完整流程推进能力
- 从任一阶段继续
- 回退到上一阶段
- 局部重跑某一步
- 确认后进入下一步
- 最终导出并打开文件

### 4. 更适合承担的交互价值
- 多栏对比
- 人工删改
- 图片 / 卡片 / 封面预览
- 排版检查
- 文件打开

## 六、CLI 作为完整命令界面，应具备的能力

CLI 不应该只是一个“跑 runner 的壳”，而应该是一个真正可操作完整流程的命令前端。

### 1. 完整流程查看能力
CLI 应能支持：
- 查看热点列表
- 查看已创建任务
- 查看某个任务当前阶段
- 查看某阶段文本内容
- 查看各平台版本
- 查看审核建议
- 查看图片与导出产物路径

### 2. 完整流程编辑能力
CLI 应能支持：
- 选择热点
- 写入热点详细内容
- 编辑母稿
- 编辑平台稿
- 应用或调整审核规则
- 修改图片生成参数
- 修改排版配置

### 3. 完整流程推进能力
CLI 应能支持：
- 从头创建内容任务
- 从任意阶段开始执行
- 单步执行
- 子流程执行
- 全流程执行（未来）
- 局部重跑
- 导出结果并返回路径

### 4. 更适合承担的交互价值
- Agent 接管任务
- 快速局部编辑
- 批量处理
- 脚本组合调用
- 自动化接入准备
- 结构化日志输出

---

## 七、两个通道共享什么

如果要做到“完整能力对齐”，就必须共享下面这些核心对象：

### 1. 共享 Task State
至少包括：
- 当前任务 ID
- 当前所处阶段
- 上一阶段输出
- 当前编辑版本
- 是否已确认
- 是否允许进入下一步

### 2. 共享 Stage Outputs
包括：
- 热点对象
- 热点补充信息
- 母稿
- 各平台稿
- 审核后版本
- 图片结果
- 排版结果
- 导出结果

### 3. 共享 Artifact Registry
用于记录：
- 每个阶段生成了哪些文件
- 每个文件对应哪个任务
- 每个版本之间的关系
- 从热点到最终成品的完整链路

### 4. 共享 Rules / Templates
包括：
- 写作策略模板
- 平台适配模板
- 去 AI 味规则
- 审核规则
- 图片提示词模板

### 5. 共享 Service / Pipeline
包括：
- Hotspot Service
- Draft Service
- Rewrite Service
- Review Service
- Visual Service
- Layout Service
- Export Service
- Workflow Runner / Stage Manager

## 八、两个通道的差异，应该体现在哪

### 1. 输入方式不同
- WebApp：表单、按钮、可视化编辑器
- CLI：命令参数、交互式输入、文本编辑、脚本调用

### 2. 呈现方式不同
- WebApp：卡片、列表、预览、多栏
- CLI：结构化文本、表格、日志、diff、路径输出

### 3. 使用节奏不同
- WebApp：适合沉浸式连续操作
- CLI：适合快速处理、批量处理、Agent 协作

### 4. 典型场景不同
- WebApp：精修、预览、排版、人工判断
- CLI：推进、批量、接管、脚本化

但注意：
- 这些只是“更适合”
- 不是“只能做”

---

## 九、对后续架构的直接要求

如果按双通道能力对齐来做，后续架构必须满足：

### 要求 1：CLI 不能只是附属 runner
CLI 必须逐步具备完整任务查看、编辑、推进能力。

### 要求 2：WebApp 不能私藏逻辑
WebApp 不能在页面和路由内部偷偷长出另一套业务实现。

### 要求 3：任务必须可跨通道续接
- WebApp 创建的任务，CLI 能继续
- CLI 修改的任务，WebApp 能接着看和导出

### 要求 4：状态模型必须先统一
如果状态模型不统一，双通道完整能力就只是口号。

---

## 十、当前阶段的结论

当前阶段先做规划，不急着全部实现。

但从现在开始，所有文档和设计口径都应统一成下面这句话：

> **WebApp 和 CLI 是同一套内容生产系统的双通道，两边都拥有完整流程能力，差异只在交互方式；所有核心逻辑统一沉到 shared core。**

---

## 十一、一句话总结

这个项目未来最合理的形态不是“网页负责一半，命令行负责一半”，而是：

> **WebApp 是完整图形前端，CLI 是完整命令前端；二者共享同一套任务状态、服务层和流程编排能力。**
