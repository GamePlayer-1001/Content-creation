# 内容生成输出项目 - 架构规划

更新时间：2026-03-19

---

## 一、架构目标

将当前项目从“多能力并存的内容工具集合”，收口成一个：

- **WebApp 为主操作面**
- **CLI 为自动化与批处理通道**
- **Shared Service / Pipeline 为统一执行核心**
- **Google Sheets 为热点输入池**
- **人工判断嵌入主流程**
- **未来可接入 OpenClaw / cron，但当前暂不接入**

的内容生产系统。

---

## 二、总架构原则

### 原则 1：双通道，不双实现
项目允许两种使用方式：
- WebApp（给人用）
- CLI（给自动化和批处理用）

但这两者**不应各自维护一套业务逻辑**。

正确做法是：
- WebApp 调用共享 Service / Pipeline
- CLI 也调用同一套 Service / Pipeline

### 原则 2：界面是操作层，不是核心逻辑层
WebApp 的价值在于：
- 可视化
- 编辑
- 审核
- 排版
- 导出

而不是承载所有业务逻辑本体。

### 原则 3：自动化应调用 CLI，不应控制页面
未来如果接入 OpenClaw / cron，应采用：

调度器 → CLI Runner → Shared Service / Pipeline → 输出结果

而不是：

调度器 → 浏览器 → 打开页面 → 点按钮

### 原则 4：主流程保留人工控制权
本项目不是纯自动化流水线，而是 **Human-in-the-loop** 的内容生产系统。

关键阶段必须允许人工参与：
- 选热点
- 补充详细内容
- 删减废话
- 调整文风
- 审核优化
- 排版定稿

---

## 三、推荐分层结构

建议整体架构分为 5 层：

### L1：输入源层（Input Sources）
负责为系统提供原始素材。

当前推荐输入源：
- Google Sheets 热点池
- 用户手动输入想法
- 用户手动输入长文本
- 用户粘贴热帖内容 / 链接摘要
- 本地模板和规则资产

说明：
- 热点抓取本身尽量与 WebApp 解耦
- WebApp 只负责消费热点池，而不承担复杂平台抓取逻辑

---

### L2：应用层（Application Surfaces）
直接面对用户或自动化调度的入口层。

#### A. WebApp
职责：
- 首页总览
- 内容生产工作流
- 工具箱
- 阶段编辑与确认
- 文件打开与结果查看

#### B. CLI
职责：
- 接收命令参数
- 触发标准流程
- 支持单步 / 多步运行
- 输出日志、状态、错误、结果摘要

说明：
- WebApp 和 CLI 只是“入口不同”
- 不应成为两套分裂的系统

---

### L3：编排层（Orchestration Layer）
负责流程编排与阶段衔接。

建议包含：
- Workflow Controller
- Stage State Manager
- Task Runner
- Retry / Resume 机制
- Output Registry

该层负责：
- 当前处于哪个阶段
- 上一步输出如何进入下一步
- 用户修改后的版本如何管理
- 哪些步骤可重跑，哪些需要重新确认

说明：
- 这是“主流程体验”的关键层
- 不能把这些逻辑散落在页面事件里

---

### L4：共享服务层（Shared Services）
这是整个项目最重要的核心层。

建议至少拆出这些服务：

#### 1. Hotspot Service
负责：
- 读取 Google Sheets 热点池
- 过滤、检索、格式化热点数据
- 将热点导入内容任务

#### 2. Draft Service
负责：
- 生成母稿
- 调用写作策略模板
- 管理输入上下文

#### 3. Platform Adaptation Service
负责：
- 针对不同平台生成适配版本
- 应用平台规则与输出格式要求

#### 4. Review Service
负责：
- 审核优化
- 去 AI 味
- 冗余删除
- 表达质量检查

#### 5. Visual Service
负责：
- 图片提示词组织
- 主配图 / 章节图 / 封面 / 卡片生成流程

#### 6. Layout Service
负责：
- 排版
- 图文结构组装
- 导出成品格式

#### 7. Export Service
负责：
- 写文件
- 输出目录组织
- 文件命名规范
- 打开文件 / 返回结果路径

#### 8. Config Service
负责：
- 统一配置读取
- 环境变量解析
- 模型 / API / 路径配置管理

说明：
- WebApp 调这些服务
- CLI 也调这些服务
- 未来自动化也应走这些服务

---

### L5：资产与输出层（Assets & Output）
负责沉淀系统长期可复用资产。

建议包含：
- 模板资产
- 规则资产
- 主题 / 视觉资产
- 输出结果资产
- 任务运行日志

资产分类建议：
- 写作策略模板
- 平台适配模板
- 去 AI 味规则
- 审核规则
- 图片提示词模板
- 封面 / 卡片 / 排版模板

输出分类建议：
- 母稿
- 平台稿
- 图片
- 封面
- 卡片
- 排版结果
- 复盘记录

---

## 四、产品层结构建议

项目产品结构只保留三块：

### 1. 首页
定位：控制台 / 总览页

建议展示：
- 最近任务
- 最近输出内容
- 热点池同步状态
- 最近导出的成品
- 快捷进入未完成工作流
- 常用工具快捷入口

### 2. 内容生产工作流
定位：项目主战场

建议按 9 步流程设计：
1. 读谷歌表格的热点列表
2. 选热点
3. 录入热点详细内容
4. 生成母稿
5. 多平台改写
6. 审核优化 / 去 AI 味
7. 生成多张配图
8. 排版
9. 导出图文结果并可打开

设计原则：
- 串行流程为主
- 每一步展示上一阶段产物
- 支持人工删改后继续
- 支持回退、局部重跑、版本保留

### 3. 工具箱
定位：专家模式 / 单独功能调用区

适合放入：
- 单独热点读取
- 单独母稿生成
- 单独平台改写
- 单独去 AI 味
- 单独图片生成
- 单独排版
- 单独导出

注意：
- 工具箱必须存在
- 但不应削弱主流程的默认入口地位

## 五、热点输入架构建议

### 当前建议
热点不直接在 WebApp 内做复杂多平台实时抓取，而采用“外部热点池 + 内部消费”的模式。

### 推荐链路
二哈定时任务 / 外部采集能力 → Google Sheets → WebApp / CLI 读取 → 导入创作

### 好处
- 降低系统耦合度
- 降低前端复杂度
- 降低平台接线维护成本
- 让“搜索”和“创作”解耦

### 当前结论
虽然热点池方案已经明确，但：
- 当前项目尚未准备好并入 cron
- 应在系统结构完善后，再接入自动化调度

---

## 六、CLI 通道规划建议

CLI 不是附属品，而是未来自动化能力的正式通道。

建议 CLI 支持以下模式：

### 1. 单步执行
例如：
- 读取热点池
- 生成母稿
- 平台改写
- 去 AI 味
- 生成图片
- 排版导出

### 2. 子流程执行
例如：
- 热点到母稿
- 母稿到多平台版本
- 平台稿到排版导出

### 3. 全流程执行（未来）
在流程成熟后，支持部分标准化场景的一键运行。

### 4. 日志与结果输出
CLI 需要明确输出：
- 成功 / 失败状态
- 错误信息
- 结果文件路径
- 运行摘要

---

## 七、文本链路资产架构建议

文本生产部分，不建议简单统称为 Prompt 模板。

建议架构如下：

### A. 写作策略层
决定：
- 观点组织方式
- 文章立意路径
- 冲突与反差结构
- 教程 / 洞察 / 叙事 / 反驳等模式

### B. 平台适配层
决定：
- 字数
- 节奏
- 语气
- 开头钩子
- 平台互动方式

### C. 质检层
决定：
- 去 AI 味规则
- 冗余删除规则
- 审核与风险控制规则

### D. 图像提示词层
决定：
- 主配图
- 章节图
- 封面
- 卡片图

这四层应分开管理，不应混为一个“提示词库”。

---

## 八、未来自动化接入建议

### 当前结论
**暂不接入 cron。**

### 未来推荐接入路径
当项目满足以下条件后，再考虑接入：
- 目录结构清晰
- 配置口径统一
- CLI Runner 稳定
- Shared Service / Pipeline 已抽离
- 关键步骤具备可重跑与日志记录能力

### 接入方式
OpenClaw cron → CLI Runner → Shared Services → 输出结果

### 人员分工建议
如果未来需要在自动化链路中对文本进行质量控制：
- 可由“写作大师”承担中间文本优化与废话删减环节

但这应建立在：
- 流程已经稳定
- 输入输出边界清楚
- 质量标准已模板化 / 规则化

之上。

---

## 九、推荐目录角色（规划层）

### 建议保留为主用
- `webapp/`
- `config/`
- `assets/`
- `output/`
- `.md/`

### 建议重点审查 / 收口
- `tools/`
- `docs/`

### 建议后续细分
- `tools/` 中区分：
  - 核心执行层
  - 历史脚本
  - 调试脚本
  - 待废弃脚本

---

## 十、一句话架构总结

这个项目最合理的最终形态，不是“纯页面工具”，也不是“纯脚本仓库”，而是：

> **WebApp 负责人类操作与判断，CLI 负责自动化与批处理，二者共用同一套底层服务与工作流编排能力。**

而在当前阶段，最重要的不是立刻接入 cron，而是先把这套架构真正收口。
