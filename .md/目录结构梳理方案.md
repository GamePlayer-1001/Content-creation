# 内容生成输出项目 - 目录结构梳理方案

更新时间：2026-03-19
状态：规划文档（先定结构，不执行迁移）

---

## 一、结论

你的判断是对的：

> 既然要做目录结构梳理，就不该只动 `webapp/` 和 `tools/`，而应该围绕项目目标，把**整个项目**按未来形态重新规划一遍。

原因很简单：
- 当前项目已经不是单一应用，而是“Web 控制台 + 配置中心 + 模板资产 + 工具脚本 + 输出资产 + 历史文档”的混合体
- 如果只收口局部目录，最后会留下大量跨目录口径漂移
- 真正影响维护成本的，不是某两个目录，而是**全局结构是否符合项目目标**

因此，本次目录梳理建议采用：

### 目标导向重画结构
不是按“历史上它放在哪”来整理，而是按“未来它应该扮演什么角色”来整理。

---

## 二、项目目标对应的目录原则

项目未来目标已经明确：

- WebApp 为主操作面
- CLI 为第二通道
- Shared Service / Pipeline 为统一执行核心
- Google Sheets 作为热点输入池
- 内容生产工作流为主路径
- 工具箱为辅助路径
- 当前先不接入 cron
- 未来允许自动化接入

基于这个目标，目录结构要满足 5 个原则：

### 原则 1：按职责分层，不按历史来源堆放

### 原则 2：主路径优先，辅助路径次之

### 原则 3：运行代码、配置资产、文档、输出结果要彻底分开

### 原则 4：历史遗留内容必须显式归档，不继续混在主干里

### 原则 5：目录一眼能看懂“哪个是主用、哪个是资产、哪个是输出、哪个是历史”

---

## 三、当前目录问题判断

当前顶层主要目录如下：

- `.claude/`
- `.md/`
- `assets/`
- `config/`
- `docs/`
- `output/`
- `templates/`
- `tools/`
- `web hot/`
- `webapp/`
- `排除/`
- 以及若干顶层文件

### 当前问题主要有这几类：

#### 1. 顶层目录语义不统一
有的是运行模块（`webapp/`），有的是资产（`assets/`），有的是文档（`docs/`），有的是输出（`output/`），也有的是临时/历史/排除目录（`排除/`、`.md/`、`web hot/`）。

#### 2. 模板被拆在多个地方
目前至少存在：
- `assets/templates/`
- `templates/`
- `config/rules/`
- `config/image-prompts.json`

说明模板、规则、提示词、视觉资源尚未形成清晰边界。

#### 3. 工具脚本过于聚集但未分层
`tools/` 里同时混有：
- 生成逻辑
- 抓取逻辑
- 发布逻辑
- 调度逻辑
- 测试
- 截图
- 视频
- 卡片渲染
- 合规工具

这导致 `tools/` 既像核心执行层，又像脚本回收站。

#### 4. 历史文档与当前文档混在一起
`docs/` 中既有仍有价值的说明，也有明显属于历史项目上下文的材料。

#### 5. 输出结果与系统运行资产边界不够清晰
`output/`、`web hot/` 都属于结果资产，但层级关系还没统一。

#### 6. “排除”目录语义不利于长期维护
`排除/` 更像一次性整理残留，不像正式项目目录。

## 四、推荐的未来顶层结构

建议将项目逐步收口为以下顶层结构：

```text
内容生成输出/
├─ app/                    # 主应用层（WebApp + CLI 入口）
├─ core/                   # 共享 service / pipeline / orchestration 核心层
├─ config/                 # 配置中心（环境变量、平台配置、模型配置、规则配置）
├─ assets/                 # 视觉素材、模板素材、静态资源
├─ knowledge/              # 文档、规划、说明、规范、历史研究资料
├─ output/                 # 生成结果与运行产物
├─ scripts/                # 辅助脚本、开发脚本、迁移脚本
├─ archive/                # 历史遗留、待淘汰、保留参考内容
├─ start.bat               # 推荐启动入口
└─ README / 项目说明        # 顶层说明
```

这是**目标结构**，不是要求一次性重命名所有目录，而是作为未来收口方向。

---

## 五、未来顶层结构详解

### 1. `app/` —— 应用层
用于放所有“用户直接接触的入口”。

建议未来包含：

```text
app/
├─ webapp/                 # Web 控制台
├─ cli/                    # CLI 入口与命令解析
└─ launcher/               # 启动器、入口封装（可选）
```

#### 放这里的内容
- `webapp/`
- 未来的 CLI Runner
- 启动相关代码

#### 不该继续放这里的内容
- 业务核心逻辑
- 各类渲染器实现细节
- 历史脚本

---

### 2. `core/` —— 共享核心层
这是未来最重要的目录。

建议未来包含：

```text
core/
├─ services/               # 共享服务
├─ pipeline/               # 串行工作流编排
├─ models/                 # 数据结构定义（可选）
├─ adapters/               # 外部接口适配（Sheets、AI Provider 等）
└─ utils/                  # 通用工具
```

#### 放这里的内容
- Hotspot Service
- Draft Service
- Rewrite Service
- Review Service
- Visual Service
- Layout Service
- Export Service
- Workflow State Manager
- Pipeline Runner

#### 目标
- WebApp 与 CLI 共用同一套执行核心
- 避免逻辑散落在 route / page / script 里

---

### 3. `config/` —— 配置中心
这个目录保留，但要内部重组。

建议未来结构：

```text
config/
├─ env/                    # 环境变量模板、示例
├─ product/                # 产品级配置
├─ platforms/              # 平台配置
├─ ai/                     # 模型 / Provider 配置
├─ rules/                  # 规则资产（审核、去 AI 味、平台规则等）
├─ prompts/                # 图片提示词、文本策略模板索引（若配置化）
└─ schedules/              # 调度相关配置（仅保留配置，不含执行器）
```

#### 说明
- `config/` 是参数和规则配置中心
- 不是“什么 json/yaml 都往里塞”的目录

---

### 4. `assets/` —— 静态资产层
这个目录保留，但需要更清晰。

建议未来结构：

```text
assets/
├─ images/                 # 图片素材
├─ themes/                 # 视觉主题
├─ covers/                 # 封面模板素材
├─ cards/                  # 卡片模板素材
├─ fonts/                  # 字体
├─ platform-ui/            # 平台模拟 UI 素材（如微信样式）
└─ demos/                  # 演示素材
```

#### 说明
- 这里放静态素材
- 文本写作模板不建议继续与视觉模板混放

---

### 5. `knowledge/` —— 知识与文档层
建议把 `docs/`、`.md/` 的职责整合到这一层语义里。

建议未来结构：

```text
knowledge/
├─ planning/               # 需求、任务板、架构规划、目录规划
├─ guides/                 # 使用说明、启动说明、操作说明
├─ governance/             # 密钥治理、合规说明、规范文档
├─ research/               # 赛道研究、案例研究、外部资料
└─ history/                # 历史体检、旧阶段总结
```

#### 说明
- `.md/` 这种目录名不适合长期项目主结构
- 文档应该从“临时文档堆”升级成正式知识层

---

### 6. `output/` —— 输出结果层
保留，但建议进一步结构化。

建议未来结构：

```text
output/
├─ drafts/                 # 母稿
├─ platform-posts/         # 平台稿
│  ├─ zhihu/
│  ├─ xiaohongshu/
│  ├─ jike/
│  ├─ x/
│  └─ ...
├─ visuals/                # 图片、封面、卡片
├─ layouts/                # 排版成品
├─ exports/                # 最终导出结果
├─ logs/                   # 运行日志
└─ reviews/                # 复盘、审核结果
```

#### 说明
- `web hot/` 长期看也应并入结果层或独立到 `output/hotspots/`

---

### 7. `scripts/` —— 辅助脚本层
建议从当前 `tools/` 中分离出“非核心但仍有价值”的脚本。

建议未来结构：

```text
scripts/
├─ dev/                    # 开发辅助脚本
├─ migration/              # 迁移脚本
├─ audit/                  # 审计、扫描、治理脚本
└─ debug/                  # 调试脚本
```

#### 说明
- 不是所有工具都应该保留在 `tools/`
- 很多更像开发辅助脚本，而不是产品能力

---

### 8. `archive/` —— 历史与待淘汰层
建议把：
- `排除/`
- 历史旧脚本
- 历史项目资料
- 待淘汰实现

统一纳入这个语义。

建议未来结构：

```text
archive/
├─ deprecated-tools/
├─ old-docs/
├─ excluded-materials/
└─ legacy-projects/
```

#### 说明
- “排除”这种名字不利于长期维护
- 应该明确它是 archive，而不是神秘黑箱

## 六、当前目录到未来结构的映射建议

### 1. 保留但重组
| 当前目录 | 未来方向 | 处理建议 |
|---|---|---|
| `webapp/` | `app/webapp/` | 保留为主操作面 |
| `config/` | `config/` | 保留，但内部重组 |
| `assets/` | `assets/` | 保留，但只放静态素材 |
| `output/` | `output/` | 保留，但按结果类型重组 |

### 2. 需要合并/升级语义
| 当前目录 | 未来方向 | 处理建议 |
|---|---|---|
| `.md/` | `knowledge/planning/` 等 | 升级为正式知识层 |
| `docs/` | `knowledge/` | 分类迁移 |
| `templates/` | `assets/` + `config/` + `knowledge/examples/` | 拆分，不整体原样保留 |
| `web hot/` | `output/hotspots/` 或 `output/trends/` | 纳入输出结果层 |
| `tools/` | `core/` + `scripts/` + `archive/` | 必须拆分，不建议整体保留 |

### 3. 需要归档/重命名
| 当前目录 | 未来方向 | 处理建议 |
|---|---|---|
| `排除/` | `archive/excluded-materials/` | 明确归档语义 |
| `.claude/` | 暂保留顶层 | 作为协作工具配置，不纳入产品结构主叙事 |

## 七、`tools/` 的重点拆分建议

当前 `tools/` 是最需要拆的目录之一。

建议未来拆成三类：

### A. 进入 `core/`
属于产品核心能力的：
- generator
- compliance（若是业务能力的一部分）
- scraper（若未来继续由项目内消费）
- 视觉生成相关核心逻辑
- output 相关核心逻辑

### B. 进入 `scripts/`
属于开发/运维辅助的：
- 审计脚本
- 一次性迁移脚本
- 手工测试脚本
- 辅助展示脚本

### C. 进入 `archive/`
历史版本或明显重复实现的：
- old/final/stealth 这类并存脚本
- 已被新实现替代的渲染器版本
- 旧调度 bat

---

## 八、`templates/` 的重点拆分建议

`templates/` 不建议继续作为一个大而统的目录长期存在。

建议拆成：

### 1. 文本策略模板 → `config/rules/` 或 `knowledge/examples/`
例如：
- 母稿模板
- 洗稿模板
- 平台适配模板

### 2. 视觉模板 → `assets/`
例如：
- 封面模板
- 卡片模板
- HTML/CSS 模板

### 3. 示例与参考案例 → `knowledge/research/` 或 `knowledge/examples/`
例如：
- 参考案例
- 平台优秀样本

---

## 九、目录梳理执行策略建议

虽然这份文档现在不执行迁移，但后续如果真的开始整理，建议按下面顺序来：

### Phase 1：先标身份，不搬家
- 给所有现有顶层目录标注：主用 / 保留 / 待拆 / 待归档
- 先形成映射表

### Phase 2：先拆语义最乱的目录
优先：
1. `tools/`
2. `templates/`
3. `docs/` + `.md/`
4. `web hot/`
5. `排除/`

### Phase 3：再升级主干结构
- 逐步形成 `app/`、`core/`、`knowledge/`、`archive/` 语义

### Phase 4：最后清理命名与文档
- 更新路径引用
- 更新启动说明
- 更新开发文档

---

## 十、当前阶段的最终建议

当前最合理的策略不是立刻大搬迁，而是：

1. 先确认未来目标目录结构
2. 先确认现有目录的角色与映射
3. 再配合双通道规划和 core/service 拆分方案
4. 最后才进入真正的物理迁移和重构

---

## 十一、一句话总结

这个项目的目录梳理，不应该是“把几个文件夹摆整齐”，而应该是：

> **围绕 WebApp + CLI 双通道、共享核心层、资产层、知识层、输出层，重画整个项目的目录结构。**
