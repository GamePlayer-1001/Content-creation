---

## 一、说明

这份文档的目的不是立刻移动文件，而是先回答两个问题：

1. **当前每个目录未来应该归到哪里？**
2. **哪些目录保留原位，哪些需要拆分、迁移、归档？**

映射原则：
- 以未来目标结构为准
- 不按历史来源保留路径
- 先定语义，再定搬迁顺序

## 五、`tools/` 目录拆分映射（重点）

### 1. 建议进入 `core/`
这些属于产品核心能力，应沉到共享核心层：

| 当前路径 | 目标方向 | 说明 |
|---|---|---|
| `tools/generator/` | `core/services/draft/` + `core/pipeline/` | 母稿生成与内容流程能力 |
| `tools/scraper/` | `core/services/hotspot/` 或 `core/adapters/` | 热点读取/抓取适配能力 |
| `tools/card/` | `core/services/visual/` + `core/services/layout/` | 卡片/封面/渲染相关核心能力 |
| `tools/cover/` | `core/services/visual/` | 封面生成 |
| `tools/compliance/` | `core/services/review/` 或 `scripts/audit/` | 若属于业务审核则进 core，否则进 scripts |
| `tools/utils/` | `core/utils/` | 通用工具 |

### 2. 建议进入 `scripts/`
这些更像辅助脚本，而不是产品核心能力：

| 当前路径 | 目标方向 | 说明 |
|---|---|---|
| `tools/show_materials.py` | `scripts/dev/` 或 `scripts/debug/` | 开发辅助 |
| `tools/manage.py` | `scripts/dev/` 或未来 `app/cli/` | 看最终是否升级为正式 CLI 入口 |
| `tools/hooks/` | `scripts/dev/hooks/` | 开发流程相关 |
| `tools/tests/` | 可保留独立 `tests/` 顶层，或 `scripts/tests/` | 取决于后续测试体系 |

### 3. 建议进入 `archive/`
这些存在明显历史版本并存问题：

| 当前路径 | 目标方向 | 说明 |
|---|---|---|
| `tools/publish/auto_publish_old.py` | `archive/deprecated-tools/publish/` | 历史旧实现 |
| `tools/publish/auto_publish_final.py` | 待判断：保留主用或归档 | 命名不适合作为长期主实现 |
| `tools/publish/auto_publish_stealth.py` | 待判断：保留主用或归档 | 需审定主实现 |
| `tools/card/render_xhs_v2.*` | 待判断：保留主用或归档 | 多版本并存需收口 |
| `tools/scheduler/run_scheduler.bat` | `archive/deprecated-tools/scheduler/` 或重做 | 当前已明显历史路径漂移 |

## 九、推荐的“先不动”清单

为了避免过早大搬迁，以下内容建议先不动：

1. `.claude/`
2. `.git/`
3. `start.bat`
4. 当前 `webapp/` 内部实现细节
5. 当前 `config/` 真实生效文件
6. 当前 `output/` 已有生产内容

这些内容应在明确迁移脚本、路径适配和引用修复策略之后再动。

## 十一、一句话总结

目录映射这一步的核心，不是“现在把文件都挪走”，而是：

> **先把现有目录全部放进未来结构模型里，明确谁保留、谁拆分、谁归档、谁迁移，再进入真正的重构实施。**
