最近三个月，我基本全量从 Claude Code 切到了 Codex。

切过来之后，有一个问题越来越困扰我，而且它在 Codex 下特别明显：

任务本身很大，主线也很清楚，但 Codex 跑着跑着就容易钻到细枝末节里。

不是它不会做。恰恰相反，是它太能做了。

一个小问题，它能继续拆；一个边角异常，它能继续挖；一个验证没过，它还能继续补环境、补脚本、补规则。最后你会发现，原本是一个产品目标，慢慢变成了一条看不到头的“继续大法”。

以前上下文窗口小，大家会比较自然地把任务切得很碎。一个小任务，一个会话，一个明确交付物。这样虽然麻烦，但边界相对清楚。

现在不一样了。

大模型上下文越来越长，一个 PRD 可以写得很完整，需求、边界、非目标、验收、阶段路线都能一次讲清楚。Agent 也真的能读进去，并且沿着一个大目标连续推进很多轮。

这当然是进步。

但在 Codex / gpt-5.x 这种很愿意继续拆、继续补、继续验证的模型特质下，它带来的副作用也很明显： **任务变大之后，人更容易失去进度感。**

这件事最消耗人的地方，不是多跑了几轮，而是你越来越难判断：

- • 现在到底完成到哪了？
- • 主线是不是已经能用了？
- • 剩下的是关键阻塞，还是可选优化？
- • 我应该让它继续，还是该停下来换下一刀？

以前我也知道要让 AI 汇报进度，但一直没找到让我舒服的格式。直到这次，我在任务结束时让 Codex 输出了两个很直观的东西：

- • 本轮完成度：80%
- • 整体目标完成度：86%

旁边再配上“已完成、已验证、未完成 / 阻塞、下一刀建议”。

我一下就舒服了。

不是因为这个百分比有多精确，而是因为它终于把一团雾变成了一个可以判断的仪表盘。

群里刚好也聊到这件事

所以这篇就写一下这个从 Claude Code 全量切到 Codex 后越来越明显的问题，以及这次我终于摸到的一点解法。

它不是一个万能方法，也不是一套标准答案，只是我在真实开发里被反复折磨之后，给 Codex 加的一条小规则： **任务结束时，必须把完成度说清楚。**

这条规则很小，但对我很有用。

AI 驱动的工程工作流，需要可控、可审、可交付

## 一、在 Codex 下，最大的问题之一不是不会做，而是太会继续

很多人刚开始用 AI 写代码，会担心它不够强。

过去三个月重度用 Codex 后，我越来越明显地感到，真正麻烦的经常不是“它做不了”，而是“它太能继续”。

尤其是 Codex 这种偏工程执行的 Agent，它很喜欢顺着一个问题继续深挖。比如你让它做一个 GUI smoke，它发现本地没有走到 native analyzer，就去查 provider；查 provider 时发现 mock 和真实路径不一致；再往下发现 Rust 某个 service 有编译问题；再往下又发现测试脚本可以优化。

这里我要加一个限定：这不是所有模型都会同样明显的问题。

我之前长期用 Claude Code，这次全量切到 Codex 后，对这个差异感受更明显。换到 Claude Code 里，这种“继续大法”的体感就没有那么强。不同模型、不同产品形态的默认行为不一样。有的更擅长按格式收口，有的更偏向继续探索；有的更容易停在边界上，有的更容易顺着工程细节一路钻下去。

所以这篇文章不是在说“所有 AI Coding 工具都这样”，而是在说我用 Codex / gpt-5.x 推大任务时，一个非常明显的模型特质。

这些事单独看都对。

但它们加起来，就会把你从主线任务拖到一堆旁支任务里。你本来想完成一个大功能，最后变成修十几个周边问题。每个问题都不大，但每个问题都能让你多花一轮。

![图片](data:image/svg+xml,%3C%3Fxml version='1.0' encoding='UTF-8'%3F%3E%3Csvg width='1px' height='1px' viewBox='0 0 1 1' version='1.1' xmlns='http://www.w3.org/2000/svg' xmlns:xlink='http://www.w3.org/1999/xlink'%3E%3Ctitle%3E%3C/title%3E%3Cg stroke='none' stroke-width='1' fill='none' fill-rule='evenodd' fill-opacity='0'%3E%3Cg transform='translate(-249.000000, -126.000000)' fill='%23FFFFFF'%3E%3Crect x='249' y='126' width='1' height='1'%3E%3C/rect%3E%3C/g%3E%3C/g%3E%3C/svg%3E)

Codex 容易把主线任务带入细节分支，导致进度变慢

这就是我说的“继续大法”。

继续本身不是错。问题在于，继续到什么时候算够？

如果没有固定收口格式，Codex 很容易把“还能做”误当成“还没完成”。而用户也会被它带着走，越看越焦虑，越看越想继续补。

最后不是代码失控，是人的判断失控。

## 二、为什么我不追求全自动，而是要保留确认点

很多人听到这里，可能会问：

既然上下文变长了，Agent 也能连续做很多轮，那为什么不让它全自动跑完？

我的真实感受是：现在还不能。

不是因为 Codex 不够努力，而是因为它背后的 gpt-5.x 模型仍然会在关键节点停下来，让人确认下一步。大部分时候，这个确认确实只是“继续”。你看一眼没问题，敲一下继续，让它往下跑。

但这个停顿并不是完全没价值。

恰恰是这些确认点，给了人一个机会：如果它开始钻牛角尖、开始无限分支、开始把一个旁支问题当成主线，你可以及时把它拉回来。

比如它任务结束时会列出：

```
完成度
- 本轮完成度：100%
- 整体目标完成度：94%

下一刀建议：
1. 补浏览器 mock 的 verification/evidence 行为
2. 改补失败 check 的修复指引
```

这种时候，人就可以判断：这两刀是不是还在主线上？是不是该继续？还是说它已经开始围着边角问题打转？

所以我现在并不把“人要确认”看成纯粹的低效。

它更像一个刹车点。

大部分时间你只是轻轻点一下继续；但一旦方向开始飘，那个确认点就变成了纠偏机会。没有这个机会，Agent 很可能会沿着一个看起来合理、但已经偏离主线的方向继续跑很远。

所以我真正想要的不是“完全无人值守”，而是：

**AI 尽可能连续推进，人只在关键收口点判断方向。**

完成度百分比正好服务这个判断点。它让你不用重新读完整过程，也能快速知道：现在是该敲继续，还是该打断它。

## 三、完成度百分比的价值，不是精确，而是让人少猜

我现在更愿意把这个百分比理解成一个“状态提示”。

它不是项目管理里的 KPI，也不是数学意义上的精确估算。它的作用很简单：

**让人快速知道，现在该继续、该暂停，还是该换方向。**

比如这次输出：

```
本轮完成度：80%
整体目标完成度：86%
```

这两个数字本身并不神奇。真正有用的是后面跟着的结构：

- • 本轮完成了什么
- • 哪些文件改了
- • 跑过哪些验证
- • 哪个验证没通过
- • 为什么没通过
- • 下一步建议先做什么

有了这些信息，我就不需要重新翻完整聊天记录，也不用从一堆终端输出里自己拼状态。

我只需要判断：

- • 80% 是否已经满足本轮目标？
- • 剩下 20% 是主线阻塞，还是环境 / 验证缺口？
- • 整体 86% 后，下一刀是否值得继续打？

这就是它真正省脑子的地方。

AI 写代码最容易让人累的，不是它写得慢，而是它让你一直处在“我是不是漏了什么”的状态里。

进度百分比把这种不确定感压成了一个可读的结论。

## 四、我后来把它写成了一条规则

这次之后，我直接把它写进了项目规则里。

大意是：

```
开发任务结束必须给完成度百分比。

非纯问答的开发任务收尾时，必须说明：
- 本轮完成度：X%
- 主线目标是否完成
- 验证情况
- 剩余缺口
- 下一刀建议

如果是路线图、长任务、多阶段主线，还要额外给：
- 整体目标完成度：Y%
- 百分比口径
```

这条规则看起来很小，但它解决的是一个特别高频的痛点。

因为 AI Coding 里最常见的失败，不是“完全做错”，而是“做了很多，但用户不知道该怎么判断”。

尤其是长任务，一旦没有收口格式，所有信息都会堆在一起：

- • 代码改动
- • 测试结果
- • 阻塞原因
- • 顺手发现的问题
- • 下一步建议
- • 额外治理事项

这些东西混在一起时，人很容易误判。

比如一个任务主线已经完成了，只是某个无关全量验证没跑完。如果 AI 不说清楚，你可能会以为任务还没完成。反过来，一个任务看起来改了很多文件，但核心 GUI smoke 没过，如果没有完成度提示，也容易被“改动很多”骗过去。

所以我现在要求它最后必须把几件事讲清楚：

**主线目标完成了吗？验证证明到哪了？剩下的是什么性质的问题？**

这比一句“任务已完成”有用得多。

## 五、为什么这类东西我更愿意放进 Rule，而不是 Skill

群里有人问，这种拆分是通过什么做的？有没有对应的 Skill 或开源项目？

我的回答很简单：

我有一个总 PRD，然后拆出优先级 plan 和执行跟踪文件，再配一组 Rule。

更具体一点，我现在在 Lime 里大概是这样组织的：

- • `docs/roadmap/` 放大的产品和架构路线图
- • `docs/exec-plans/` 放每一条执行计划、进度日志、阻塞记录和验证证据
- • `AGENTS.md` 放仓库级硬规则，约束 Codex 每次怎么工作、怎么收口

`roadmap` 解决的是“为什么做、做成什么样、哪些不做”。比如 AI 图层化设计路线图里，会先固定北极星：从“输出一张图片”升级为“输出可编辑设计工程”。然后继续写事实源、非目标、阶段、验收总线。

`exec-plans` 解决的是“今天怎么推进”。它会把路线图拆成 P0、P1、P2，一刀一刀落下去；每一刀做了什么、没做什么、验证了什么、下一刀应该打哪里，都要写回去。

所以现在的工作方式，不是把大需求硬拆成一堆互相断开的短会话，而是：

```
大 PRD / roadmap 定方向
  -> exec plan 拆阶段
  -> 每一轮只打一刀
  -> 进度日志持续回写
  -> 收尾时给完成度和下一刀
```

这套做法和 1M 上下文很搭。

因为上下文变长之后，AI 确实可以理解更大的目标；但越是这样，越不能只靠聊天窗口里的临时记忆。大目标必须有 versioned artifact 承载，执行过程必须有 plan 文件切分，任务结束必须有状态汇报。

AI 编程大任务的三层工作法：路线图、执行计划、项目规则

我不太喜欢事事都用 Skill。

不是 Skill 不好，而是很多东西还没到 Skill 的层级。像“任务结束必须给完成度百分比”这种要求，本质上不是某个专项能力，而是整个项目的工作习惯。

这种东西放在 `AGENTS.md` 里更合适。

Rule 的好处是，Agent 进入项目就会读到。它不需要你每次想起来再触发，也不需要指定某个目录。它更像项目里的交通规则，不是某个工具箱里的螺丝刀。

我现在的做法是：

- • `AGENTS.md` 只放仓库级硬规则，尽量控制在 100 行左右
- • 更长的工程说明下沉到 `docs/aiprompts/`
- • 具体执行计划放到 `docs/exec-plans/`
- • 高频、稳定、边界清楚的问题，再沉淀成 Skill

这套结构对我来说比较舒服。

因为它没有一上来就把所有东西都 Skill 化。

先用 Rule 控制底层行为，再用文档承载细节，最后把真正反复出现、值得复用的流程升级成 Skill。这个顺序对我来说更自然，也更不容易把系统搞重。

## 六、Skill 是私人化资产，不是装得越多越好

这次群里还有一个讨论我很认同：

Skill 其实非常私人化。

别人的 Skill 可以参考，可以复刻，可以拆开看，但很少能直接装上就完全适合你。

原因也不复杂。

每个项目的痛点不一样，每个人的控制习惯也不一样。有人更重测试，有人更重产品节奏；有人喜欢强规划，有人喜欢先动手再收口；有人做 Web，有人做桌面 GUI；有人在意发布，有人在意治理。

这些差异最后都会体现在 Rule、Skill、Prompt 和执行计划里。

所以我越来越觉得，Skill 不是“别人给你一套最强装备”，而是你自己在项目里一点点长出来的手感。

你只有真的痛过，才知道该加哪条规则。

你只有真的被某类问题反复卡住，才知道它值得不值得变成 Skill。

一上来搞一个大而全的 Skill 包，听起来很厉害，但你可能根本不知道哪些有用，哪些会干扰你。

![图片](data:image/svg+xml,%3C%3Fxml version='1.0' encoding='UTF-8'%3F%3E%3Csvg width='1px' height='1px' viewBox='0 0 1 1' version='1.1' xmlns='http://www.w3.org/2000/svg' xmlns:xlink='http://www.w3.org/1999/xlink'%3E%3Ctitle%3E%3C/title%3E%3Cg stroke='none' stroke-width='1' fill='none' fill-rule='evenodd' fill-opacity='0'%3E%3Cg transform='translate(-249.000000, -126.000000)' fill='%23FFFFFF'%3E%3Crect x='249' y='126' width='1' height='1'%3E%3C/rect%3E%3C/g%3E%3C/g%3E%3C/svg%3E)

Skill、Prompt、Rule 更像练车手感，不是整套赛车手技巧直接复制

这和学开车很像。

一个刚开始练车的人，最需要的不是赛车手的全套技巧。什么走线、刹车点、油门控制、极限过弯，当然都高级，但你连方向盘、刹车、后视镜、车距都还没形成体感时，这些东西反而会变成负担。

你真正需要的是先开起来。

先知道自己什么时候慌，什么时候看漏，什么时候容易打多方向，什么时候该慢下来。等这些问题真的出现过几次，你再去学对应的技巧，才会知道它到底解决什么。

Skill 也是一样。

别人开源的 Skill，很多时候就像赛车手的训练手册。它当然有价值，但不是每一页都适合你当前阶段。你直接整套搬进来，可能 80% 都用不上，甚至会让 AI 在你还没建立基本控制感的时候，多出一堆你也判断不了的自动动作。

更好的顺序是：

- • 先用基础 Rule 把车开稳
- • 再用 Prompt 解决眼前的具体问题
- • 反复痛过的问题，沉淀成项目文档
- • 高频、稳定、边界清楚的流程，再升级成 Skill

这样长出来的 Skill，才是你的 Skill。它不是别人给你塞进来的装备，而是你自己练出来的控制感。

AI Coding 也是一样。

而且这件事不只适用于新手。

就算你已经是老手，换到一个从零开始的新项目，也不应该把旧项目里的全部 Skills、Prompt、Rule 一股脑复制过去。

老手当然有经验，但经验不是整包迁移。一个项目的规则，往往是被这个项目自己的痛点磨出来的。旧项目里很重要的治理规则，在新项目里可能暂时用不上；旧项目里非常顺手的 Skill，换了技术栈、产品阶段、团队协作方式，也可能会变成噪音。

真正能迁移的不是那一整套文件，而是判断力：

- • 哪些痛点已经在新项目里出现了
- • 哪些规则应该立刻带过来
- • 哪些先放在脑子里，不急着写进项目
- • 哪些等它反复出现，再沉淀成 Skill

所以我更愿意把旧项目的 Rules、Prompt、Skills 当成素材库，而不是启动模板。

新项目要有自己的生长过程。老手的优势，不是复制得更快，而是更快判断哪些东西现在该带，哪些东西以后再说。

## 七、真正要建立的是自己的 harness

我后来越来越喜欢用 `harness` 这个词。

它不只是 Prompt，也不只是 Skill，更不是某个单独工具。

它是一整套你和 AI 协作时的操控系统：

- • 任务怎么拆
- • 进度怎么报
- • 文档落在哪里
- • 规则放在哪里
- • 什么情况必须验证
- • 什么情况应该停手
- • 哪些问题可以顺手修
- • 哪些问题只能登记，不能偏航

这些东西加起来，才是你真正的 AI 开发手感。

这也是为什么我会说，适合自己的才是最好的。别人的经验很重要，但最后一定要回到自己的项目里试。

别人开源的 Rule、Skill、Prompt 都有价值，但它们最多是参考答案。你要把它们改成自己的节奏，自己的项目边界，自己的判断习惯。

比如这次的“完成度百分比”，它不是一个复杂技巧，但对我很有用，因为它刚好解决了我在大任务里最痛的一点：

**我需要随时知道，主线到底走到哪了。**

所以真正要练的，不是“收集 Skills 的能力”，而是“沉淀 Skills、Prompt、Rule 的能力”。

从真实痛点沉淀技能、提示词、规则的能力飞轮

这是一种更底层的能力：

- • 你要能感知自己在哪里被 AI 拖累
- • 你要能判断这是一次性问题，还是会反复出现的问题
- • 你要能决定它应该变成一句 Rule、一段 Prompt，还是一个完整 Skill
- • 你还要能在项目变化后，把旧规则删掉、改掉、降级，而不是越堆越多

这套能力练出来以后，你就不会太迷信任何现成方案。看到别人好的 Skill，可以吸收；看到别人好的 Prompt，可以改造；看到别人好的 Rule，可以先试。但最后它们都要经过你的项目、你的工作流、你的痛点重新筛一遍。

AI 开发的长期效率，最后拼的不是谁装得多，而是谁更会把自己的经验沉淀成一套能持续进化的操作系统。

## 八、可以直接抄走的一条规则

如果你也经常被 AI 的“继续大法”拖着走，可以先不用搞复杂系统，直接在项目规则里加这一段：

```
开发任务结束必须给完成度百分比。

收尾时必须说明：
1. 本轮完成度：X%
2. 主线目标是否完成
3. 已完成的关键改动
4. 已执行的验证
5. 未完成 / 阻塞项
6. 下一刀建议

如果任务属于路线图、长任务或多阶段主线，还必须说明：
1. 整体目标完成度：Y%
2. 百分比口径
```

再补一句更关键的：

```
先回答主线是否完成，再回答周边是否完成。
不要把可选优化、额外治理、无关验证缺口混进主线完成状态里。
```

这句话很重要。

否则 AI 很容易因为“还可以继续优化”而把一个已经能交付的任务说成“还没完成”；也可能因为“改了很多东西”而把一个主线没验证的任务说得太乐观。

好的收口不是为了显得专业，而是为了让人更快做判断。

## 九、最后

这次最大的体悟其实很朴素：

AI Coding 的关键，不只是让 Agent 更聪明，也不是装更多 Skill。

真正关键的是，你要一点点建立自己的操控规则。

痛在哪里，规则就长在哪里。

反复出现的问题，再沉淀成 Skill。

项目长期需要的知识，落到文档和执行计划里。

任务结束时，用完成度百分比把状态讲清楚。

中途需要确认时，不要机械地一直敲继续。大部分时候可以继续，但只要它开始无限分支、钻旁支细节，就要及时纠正。

这样人就不会被 AI 的“继续大法”拖着跑，而是能重新掌握节奏。

我现在才真正 get 到，为什么 Claude Code 那类 format style output 会有价值。

它不是形式主义。

它是在帮人少烧脑。

而 AI 开发到最后，很多时候拼的不是谁多跑了几轮，而是谁能在复杂上下文里更快判断：

**现在够了吗？下一步打哪里？**
