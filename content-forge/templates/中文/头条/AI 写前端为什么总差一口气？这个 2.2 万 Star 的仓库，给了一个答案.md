## AI 写前端为什么总差一口气？这个 2.2 万 Star 的仓库，给了一个更稳的答案

如果你最近在用 Claude Code、Cursor、Codex 这类 AI 编程工具做前端，应该都会有一种很熟悉的感觉：

它们不是不会写页面。

恰恰相反，它们往往写得很快。

问题是， **写出来的东西经常差一口气** 。

有时候是颜色不稳。

有时候是层级不稳。

有时候第一屏还挺像样，往下继续做两页，整个风格就开始飘。

按钮、卡片、留白、字重、圆角、阴影，明明都不是什么高深问题，但只要没有明确约束，AI 每一轮都会重新“猜一次设计”。

我最近看到一个很有意思的仓库：  
VoltAgent/awesome-design-md。

它不是在教 AI 怎么写组件，也不是在卖新的设计工具。

它做的事情非常简单，但很可能会越来越重要：

**把“项目应该长什么样”这件事，写成一份 AI 能直接读懂的 DESIGN.md。**

如果只看一句话，我对这个仓库的判断是：

**它真正值得关注的，不是收集了多少设计文件，而是它让 AI 写 UI 这件事，第一次有了一个足够轻、足够直接、又足够像工程协作文件的设计约束层。**

## 一、这类仓库为什么现在值得看

先说结论。

awesome-design-md 值得写，不是因为它是又一个 awesome 列表。

而是因为它踩在一个很新的变化上：

**AI coding 正在从“会生成页面”，走向“需要持续生成一致页面”。**

这两件事看起来很像，其实不是一个难度层级。

前者解决的是“能不能做出来”。

后者解决的是“第二页、第三页、下一个功能、下周新加的模块，还能不能和第一版长得像同一个产品”。

这恰恰是今天很多 AI 前端工作流最缺的一层。

你给它一张截图，它能模仿。

你给它一句 prompt，它也能拼出一个大概。

但只要项目往前走，设计一致性就会开始掉。

于是你会发现，真正耗时间的不是“让 AI 生成第一版”，而是后面不停地修：

- 这个按钮怎么又换了圆角
- 这个页面怎么又换了标题层级
- 为什么新模块的间距和前面不一样
- 这个深色主题为什么又像另一套产品

所以问题慢慢变成了：

**我们要不要给 AI 一份稳定的设计说明书？**

而 DESIGN.md，就是现在最值得看的那个答案之一。

## 二、DESIGN.md到底是什么

按 Google Stitch 官方文档的定义，DESIGN.md 本质上是一份给 AI 代理读取的纯文本设计系统文档。

你可以把它理解成：

- 不是给设计师看的 Figma 文件
- 不是给浏览器解析的 token JSON
- 也不是一段临时 prompt

而是一份放在项目根目录、让 AI 每次开工前都能先读一遍的设计规则文件。

这个概念最妙的地方就在这里。

它足够轻。

就是一个 markdown 文件。

不用导出，不用转格式，不用接复杂协议。

但它又足够稳。

因为里面写的不是“帮我做个高级一点的页面”，而是：

- 颜色怎么用
- 字体怎么分层
- 间距按什么尺度走
- 卡片、按钮、输入框长什么样
- 暗色模式怎么处理
- 哪些做法不要碰

说白了，它是在把“设计感觉”翻译成 AI 能稳定复用的工程文本。

这也是为什么 awesome-design-md 这个仓库会有意思。

它不是在发明 DESIGN.md。

它做的是另一件更实用的事：

**把一批真实网站的设计风格，提炼成现成可复制的 DESIGN.md。**

## 三、这个仓库到底提供了什么

我看了 README，它现在最有价值的信息不是“收录了很多网站”，而是它把使用门槛降得非常低。

逻辑几乎可以压成 2 步：

1. 从仓库里挑一个你喜欢的网站风格
2. 把对应的 DESIGN.md 复制到项目根目录，然后告诉 AI 按它来做

就这么直接。

截至我查询 GitHub API 的时间，也就是 **2026 年 4 月 7 日** ，这个仓库已经有 **22,707 stars** 。README 当前展示的是 **58 份 DESIGN.md** 。

收录对象也很聪明，基本都是开发者和产品团队熟悉的网站：

- Stripe
- Vercel
- Linear
- Notion
- Apple
- NVIDIA
- Cursor
- Supabase
- Resend
- Zapier

这意味着它不是在给你抽象审美课。

而是在给你现成的“参考站风格说明书”。

而且 README 里写得很清楚，每个站点目录里通常不只有 DESIGN.md，还会带：

- preview.html
- preview-dark.html

这两个预览文件很关键。

因为它把“设计规则文本”和“可视化校验”放到了一起。

这样你不是闭着眼把文件塞给 AI，而是可以先看一眼：

这套颜色、字体、按钮、卡片，到底是不是你想要的方向。

## 四、它真正补上的，不是审美，而是“持续一致性”

我觉得这篇最重要的一句，不是“这个仓库很好用”。

而是：

**DESIGN.md 补上的不是灵感，而是持续一致性。**

很多人以为 AI 写 UI 最大的问题是“不够好看”。

其实往往不是。

很多时候它第一屏已经够用了。

真正麻烦的是，它很难在后续迭代里一直保持同一种设计语法。

而一旦没有这层一致性，项目就会出现一种很常见的状态：

- 单看每个页面都还能用
- 合在一起却不像同一个产品

这件事对独立开发者尤其痛。

因为你本来就不是全职设计师。

你想要的不是每次都重新指导 AI 一遍，而是：

**我已经确定过一次风格，后面请一直照这个来。**

这正是 DESIGN.md 这类文件最像工程协作资产的地方。

它不像 prompt 那样每次都要重讲。

它也不像截图那样只能参考一个瞬间。

它更像 AGENTS.md 的设计版本：

- AGENTS.md 约束怎么做
- DESIGN.md 约束做成什么样

这个对应关系在 awesome-design-md 的 README 里写得很明白，我觉得这个比“58 份文件”本身更值得记住。

## 五、为什么说它比截图提示词更稳

很多人现在做 AI 前端，已经会用一种很常见的办法：

- 找一个喜欢的网站截图
- 告诉 AI 照这个风格来

这当然有用。

但它的问题也很明显。

截图更像一个静态结果。

它能告诉 AI “看起来差不多像这样”，但很难稳定表达：

- 配色的语义角色
- 字号层级的规则
- 间距尺度的规律
- 交互态和组件态的约束
- 响应式时哪些东西该折叠、哪些不该动

这些东西，恰恰决定了一个产品是不是“越做越像一套系统”。

所以如果你只是做一张 landing page，截图模仿可能够。

但如果你要继续做：

- 定价页
- 控制台
- 设置页
- 表单流
- 深色模式

那纯截图引导就很容易失效。

而 DESIGN.md 更像是把“看起来像”升级成“规则上也对齐”。

## 六、这个仓库最适合谁用

我觉得最适合 4 类人。

## 1\. 正在用 AI 快速做产品原型的独立开发者

这类人最大的问题不是做不出来，而是每次新页面都像另一个项目。

## 2\. 没有专职设计师，但又不想让产品越做越乱的小团队

他们最需要的不是最强设计，而是一套能反复复用的稳定设计语言。

## 3\. 已经在用 Claude Code / Cursor / Codex 做前端的人

这类人会很快理解 DESIGN.md 的价值，因为他们已经吃过“一路往后写，UI 逐渐漂移”的亏。

## 4\. 想研究 AI 设计协作工作流的人

这个仓库本身就是一个很好的观察样本。

它让我们看到，未来 AI 协作文件可能不只会有：

- AGENTS.md
- TASKS.md
- MEMORY.md

还会有一类设计层文件。

## 七、它也不是没有边界

这类东西也别神化。

DESIGN.md 很重要，但它不是万能钥匙。

至少有三个边界要讲清楚。

## 1\. 它解决不了产品结构问题

如果信息架构本身就乱，DESIGN.md 也救不了。

它能保证的是风格一致，不是产品逻辑自动正确。

## 2\. 它更适合“已有方向后的稳定复用”

如果你连产品应该长什么样都没想清楚，那直接套 DESIGN.md 也可能只是更稳定地做错。

## 3\. 它解决的是大部分一致性，不是全部设计判断

真正复杂的品牌设计、动效、图形语言、插画系统，还是会超出一个 markdown 文件能完整表达的范围。

所以我更愿意把它理解成：

**一层很轻但非常有用的设计约束层。**

不是终点，但很可能是 AI 前端工作流里必须补的一层。

## 八、如果你想试，最好的方式不是“研究完再说”

这类仓库最怕一种用法：

收藏了，觉得很对，然后没有然后。

如果你真想验证它值不值，最简单的办法其实很直接。

## 第一步：挑一个你本来就喜欢的网站风格

比如你喜欢：

- Linear
- Stripe
- Notion
- Vercel

先别追求最复杂，先选你本来就知道自己喜欢的那种风格。

## 第二步：把对应的 DESIGN.md放进项目根目录

让 AI 后续做页面时优先读取它。

## 第三步：连续做 3 个页面

不要只做第一屏。

至少做：

- 首页
- 一个内页
- 一个表单或设置页

因为只有做到第三页，你才能看出一致性到底有没有真的提高。

## 九、最后怎么理解这个仓库

如果你只把 awesome-design-md 看成一个收集风格文件的仓库，那你其实只看到了它最表面的一层。

它真正值得关注的地方，是它在提醒我们一件事：

**AI 编程开始不只是需要 prompt，也开始需要稳定、结构化、可复用的协作文件。**

AGENTS.md 解决的是“怎么做”。

DESIGN.md 解决的是“做成什么样”。

而像 awesome-design-md 这样的仓库，等于把这件事从抽象概念，变成了一个你今天就能试的实际工作流。

如果你最近刚好也在用 AI 做前端，最值得试的不是一下子研究完整套方法论。

而是先拿一个你本来就喜欢的网站风格，放进项目里，连续做 3 个页面，看看一致性是不是真的上来了。

很多时候，你会比单看介绍更快感受到它的价值。
