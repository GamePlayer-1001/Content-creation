## social-auto-upload：一键多平台视频分发，收敛成一套 CLI + Skill + Agent 工作流

> "很多人以为多平台分发难点在内容生产，真正做起来才发现，最消耗时间的是重复上传、重复检查、重复设定发布时间。 `social-auto-upload` 的价值，不只是自动上传，而是把这件事逐步整理成一套能给人用、也能给 Agent 用的标准流程。"

### 为什么需要这个项目？

只要你同时运营两个以上平台，很快就会遇到一个很现实的问题：内容也许是同一条，但平台的登录、上传、参数、发布时间、封面和账号状态，几乎都要重复处理一遍。

- **痛点 1：重复上传是高频但低价值的劳动** 。视频剪完之后，真正耗人的常常不是创作，而是一遍遍点开后台、填标题、传封面、设时间。
- **痛点 2：同一套内容在不同平台要走不同流程** 。抖音、小红书、快手、B 站，参数和交互都不一样，很难靠单一脚本长期维护。
- **痛点 3：Agent 看得懂网页，不代表适合做重复执行** 。让 Agent 每次都临场识别页面、截图理解、重新判断按钮位置，成本高，稳定性也未必够。
- **痛点 4：真正可落地的不是“能跑一次”，而是“能反复用”** 。创作者和运营更需要的是可验证、可复用、可定时、可切账号的工作流。

`social-auto-upload` 现在在做的，就是把“多平台分发”从一堆零散脚本，逐步收敛成统一 CLI、平台 skill 和面向 Agent 的 bootstrap 文档。这样你不只是得到一个仓库，而是得到一条更接近真实生产的执行链路。

> "上传不是创作，但它会持续吞掉创作者最宝贵的注意力。"

### 核心内容

#### 1\. 先把多平台上传这件事做成统一入口

这个项目的整体目标很直接：自动化上传视频到多个社交媒体平台。README 里列出的覆盖范围包括：

- **抖音**
- **Bilibili**
- **小红书**
- **快手**
- **视频号**
- **百家号**
- **TikTok**

但更值得注意的是，它不是停留在“平台很多”这一步，而是在把高频使用场景逐步往统一入口上收。

#### 2\. 当前主线已经开始围绕 sau CLI 收敛

仓库当前主线提供统一命令入口 `sau` 。根据 `docs/CLI.md` 和 `docs/agent-bootstrap.md` ，目前主线接入最完整的是：

- **douyin**
- **kuaishou**
- **xiaohongshu**
- **bilibili**

这意味着它已经不只是“给开发者读源码的项目”，而是在往真正能执行的命令行工具演进。对日常运营来说，这一步很关键，因为可调用的 CLI 比零散脚本更容易接入自动任务、计划任务和 Agent。

#### 3\. 不只支持视频，也在补齐图文和定时发布

从 README 和 CLI 文档看，这个项目当前已经覆盖了几类很实用的能力：

- **账号登录 / 账号检查**
- **视频上传**
- **图文上传**
- **定时发布**
- **多账号管理**

其中一个很实用的点是元数据约定开始统一了：

- **视频走 `title + desc + tags`**
- **图文走 `title + note + tags`**

这种统一约定看起来朴素，但它会直接影响后续是不是容易批量化、是不是容易被别的脚本或 Agent 接管。

#### 4\. 它已经明显开始为 Agent 场景写文档和 skill

这是这个项目和普通“自动上传脚本”最大的差异之一。

仓库里不只给了安装说明，还单独给了：

- **Agent Bootstrap Prompt**
- **CLI 使用说明**
- **各平台 skill 目录**

文档里明确点名了 `OpenClaw` 、 `Codex` 、 `Claude Code / cc` 这些 Agent 客户端，并且强调：

- 优先使用 `uv`
- 优先使用 `sau`
- 优先参考 `docs/install.md` 、 `docs/CLI.md`
- 不要默认走历史 `examples/` 和旧 Web 路径

这说明作者已经不满足于“给人看教程”，而是在主动把仓库整理成“更适合交给 AI 执行”的形态。

#### 5\. 项目现在处在一轮主线重构期

README 在 `2026-03-24` 的近况说明里写得很明确：项目正在进入一段相对密集更新的阶段，当前重构重点包括：

- **各平台 uploader 结构收敛**
- **CLI 统一接入**
- **面向 Agent 的 skill 化**
- **切到 `patchright` 驱动**
- **主线优先围绕无头模式推进**

换句话说，这不是一个“已经彻底稳定、不再变化”的成品，而是一个已经跑出价值、同时正在往更标准化方向收紧的项目。

### 技术亮点

- **统一 CLI 入口开始成型** ： `sau` 把多平台操作收敛到同一套命令体系里，这比只提供 `examples/` 脚本更适合长期使用。
- **对 Agent 很友好** ：仓库不仅有代码，还有专门的 bootstrap prompt 和平台 skill，这会明显降低“把仓库交给 AI 后跑偏”的概率。
- **安装链路比很多同类项目更清楚** ：当前主线优先使用 `uv pip install -e .`，并用 `pyproject.toml` 注册 `sau` 命令，路径比旧式 requirements 方案更清晰。
- **浏览器自动化路线有明确取舍** ：项目正在转向 `patchright` ，并优先围绕无头模式推进，明显是在考虑稳定性、兼容性和自动化场景。
- **不仅支持上传，还支持定时发布** ：对于真正做内容矩阵的人来说，定时能力比“能上传一次”更接近业务价值。

### 如何开始学习

- **第一步先看 README 和安装说明** ：先确认你需要的是当前 CLI 主线，而不是历史脚本或旧 Web 入口。
- **第二步按主线方式安装** ：优先用 `uv` 建环境，再执行 `uv pip install -e .`，让 `sau` 命令可用。
- **第三步先做 CLI 验证** ：至少确认 `sau --help` 以及几个平台子命令都能正常输出。
- **第四步再进入具体平台** ：根据目标平台去跑登录、账号检查、视频上传或图文上传。
- **第五步再考虑交给 Agent** ：如果你本来就想让 AI 帮你做执行，把仓库和 `docs/agent-bootstrap.md` 一起交给 Agent，效率会更高。

建议路径：

- **普通创作者** ：先用 CLI 跑通一个平台，再决定是否扩展到更多平台
- **技术用户** ：先验证 `sau` ，再读 `skills/` 和 `uploader/`
- **Agent 用户** ：直接从 bootstrap prompt 开始，不要一上来就自由探索整个仓库

### 项目特色

#### 特色 1：它解决的是“最后一公里重复劳动”

很多项目更关心内容生成，但真正做矩阵分发的人会发现，上传和定时发布本身就是一个巨大的时间黑洞。 `social-auto-upload` 对准的正是这块。

#### 特色 2：它不是只服务人，也开始服务 Agent

仓库里专门为 Agent 写安装与执行提示词，这意味着它已经在适配新的使用方式: 人不一定亲自点后台，Agent 也可以接管执行步骤。

#### 特色 3：它不是简单堆平台，而是在做能力收敛

真正难的不是支持七八个平台，而是把这些平台逐步整理到统一接口、统一元数据和统一验证路径里。这个项目现在正处在这个阶段。

#### 特色 4：它承认历史路径存在，但明确主线优先级

README 明确写了当前主线、历史 `examples/` 、历史 Web 的关系。对实际使用者来说，这种“告诉你别走错路”的说明，比单纯展示功能更重要。

#### 特色 5：它已经被真实需求推到了重构阶段

截至 `2026-03-27` ，GitHub API 显示该仓库有 `9350` Stars、 `1678` Forks，最近一次代码推送时间是 `2026-03-26T12:24:01Z` 。这说明它不是没人用的实验项目，而是已经被真实用户需求持续推动。

#### 特色 6：Release 节奏和主线进展并不完全同步

GitHub 最新公开 Release 仍然是 `oh-v1.0` ，发布时间为 `2024-04-10` ，标题是 `feature: tiktok upload` 。但仓库主线在 `2026-03` 仍在持续重构，这提醒我们：判断项目活跃度时，不能只看 Release，还要结合 README 和最近提交时间一起看。
